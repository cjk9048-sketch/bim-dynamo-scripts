# Civil 3D 종단 밴드 수직부 계획고 두 줄 표기 — 해결방안

## 1. 핵심 결론

현재 문제는 `Profile` 자체를 억지로 수정해서 해결하기보다, **실제 계획 종단 데이터와 수직부의 표시 데이터를 분리하는 방식**이 가장 안정적이다.

Civil 3D의 `Profile`은 한 Station에서 하나의 Elevation을 가지는 구조이므로, 옹벽·가시설 등의 수직부처럼 한 측점에서 앞·뒤 두 계획고를 동시에 표현해야 하는 경우에는 Profile 데이터 자체에서 이를 직접 표현하려 하지 않는 것이 좋다.

권장 구조는 다음과 같다.

```text
                    DH.Grading
                        │
                 ┌──────┴──────┐
                 │             │
             일반구간        수직부
                 │             │
          Civil 3D 기본밴드    WallSpan
                 │             │
             계획고 1개      Front / Back
                               │
                               ▼
                    VerticalGradeAnnotation
                               │
                         ┌─────┴─────┐
                         │           │
                    Front Text   Back Text
```

즉,

- `Civil 3D Profile` → 계산용 단일 계획고
- `WallSpan` → 수직부의 Front/Back 두 계획고 정보
- Civil 3D 기본 Band → 일반구간 표시
- 애드인 자체 Annotation → 수직부 두 줄 표시

로 역할을 분리한다.

---

## 2. 현재 접근에서 유지할 부분

현재 코드에는 이미 수직부의 앞·뒤 측점을 계산하는 `WallSpan(Mid, Front, Back)` 구조가 있다.

```csharp
WallSpan
{
    Mid,
    Front,
    Back
}
```

이 구조를 수직부 표시의 기준 데이터로 계속 사용하는 것이 좋다.

계획 Profile에서 다음과 같이 표고를 얻는다.

```csharp
FrontZ = pad.ElevationAt(front);
BackZ  = pad.ElevationAt(back);
```

이렇게 얻은 두 표고를 수직부의 표시 데이터로 사용한다.

---

## 3. 일반구간과 수직부를 분리한다

### 일반 측점

Civil 3D의 기본 계획고 밴드를 그대로 사용한다.

```text
No.5+00       184.10
No.5+05       184.20
No.5+10       184.30
```

### 수직부

수직부 Station에서는 기본 계획고 Label을 숨기고 애드인이 두 줄을 별도로 표시한다.

```text
No.5+12.34
184.10
189.10
```

즉 현재 접근인

1. 기본 계획고 Label 숨김
2. DBText 두 개 생성

이라는 방향 자체는 타당하다.

다만 LabelGroup을 찾는 방법은 개선해야 한다.

---

## 4. Y순서로 LabelGroup을 추정하는 방식은 최종 코드에서 제거

현재 임시 방식은 밴드 라벨 그룹 수와 밴드 칸 수가 같다는 가정하에 평균 Y값으로 정렬한다.

```csharp
groupsY.Sort((a, b) => b.Y.CompareTo(a.Y));
picks.Add(groupsY[planIdx].G);
```

이 방식은 다음 상황에서 깨질 가능성이 있다.

- 어떤 밴드에 라벨이 없음
- 하나의 밴드에서 라벨이 2개 이상 생성됨
- 밴드 스타일 변경
- 템플릿 변경
- Civil 3D 버전 변경
- LabelGroup 생성 순서 변경

따라서 이 방식은 디버깅용 임시 방법으로만 사용하고 최종 구현에서는 제거하는 것을 권장한다.

---

## 5. LabelGroup → Band를 역추적하지 않는 방향으로 변경

현재 가장 중요한 문제는 다음과 같다.

- `LabelGroup.StyleName`에서는 "계획"이라는 이름을 찾기 어려움
- 반면 `ProfileViewBandItem`의 `BandStyleId`에서는 계획고 스타일 이름을 확인할 수 있음

따라서 방향을 반대로 잡는다.

### 좋지 않은 접근

```text
LabelGroup
    ↓
어느 Band가 만들었는지 추적
```

### 권장 접근

```text
ProfileView
    ↓
Bands
    ↓
BandItem
    ↓
BandStyleId
    ↓
계획고 Band 확정
```

현재 횡단면도에서 사용하고 있는 것처럼 `sv.Bands.GetBottomBandItems()`를 이용해 BandStyle을 확인하는 방식을 활용한다.

예를 들어:

```csharp
using var items = sv.Bands.GetBottomBandItems();

var sb = tr.GetObject(
    items[i].BandStyleId,
    OpenMode.ForRead
) as StyleBase;

// sb.Name
// "DH_횡단 뷰_횡단 데이터_지반고"
// "DH_횡단 뷰_횡단 데이터_계획고"
```

종단 밴드에서도 가능한 범위 내에서 동일한 원칙으로 계획고 Band를 먼저 확정하고, 그 Band의 표시 대상만 처리하는 구조가 좋다.

---

## 6. DBText 방식은 사용할 수 있지만 "애드인이 관리하는 Annotation"으로 취급

DBText 자체가 문제는 아니다.

오히려 현재 애드인의 구조에서는 DBText를 사용해 수직부의 두 값을 직접 그리는 것이 현실적인 해결책이다.

다만 단순히 도면에 DBText를 뿌리는 것이 아니라 **수직부 표기 객체를 애드인이 관리하는 구조**로 만드는 것이 좋다.

예시:

```csharp
class VerticalGradeAnnotation
{
    public ObjectId ProfileViewId { get; set; }

    public double Station { get; set; }

    public double FrontElevation { get; set; }

    public double BackElevation { get; set; }

    public ObjectId FrontTextId { get; set; }

    public ObjectId BackTextId { get; set; }
}
```

이렇게 하면 수직부의 표시와 원본 데이터를 명확하게 연결할 수 있다.

---

## 7. 별도 레이어를 만들어 관리

예를 들어 다음과 같은 전용 레이어를 사용한다.

```text
DH_GRADING_VERTICAL_GRADE
```

수직부 두 줄 표기를 모두 이 레이어에서 관리한다.

그러면 업데이트할 때 해당 레이어의 기존 객체만 제거하고 다시 생성할 수 있다.

---

## 8. 재생성 방식으로 업데이트

DBText는 선형이나 측점이 변경되었을 때 Civil 3D Label처럼 자동으로 따라가지 않는다.

따라서 현재 애드인의 구조에서는 **재계산 후 재생성 방식**이 현실적이다.

권장 흐름:

```text
기존 수직부 표기 삭제
        ↓
WallSpan 재계산
        ↓
Front / Back Station 계산
        ↓
현재 Profile에서 Front / Back Elevation 계산
        ↓
수직부 두 줄 표기 재생성
```

현재 코드에서도 수직부 표기를 다시 그리는 방식과 잘 맞는다.

---

## 9. 두 번째 Profile을 만드는 방식은 비추천

다음과 같이 별도 Profile을 두 개 만드는 방법도 생각할 수 있다.

```text
Profile A = 옹벽 상단
Profile B = 옹벽 하단
```

하지만 이 문제를 해결하기 위해서는 지나치게 복잡해질 가능성이 높다.

Profile을 두 개로 분리하면 이후 다음 요소들을 계속 동기화해야 한다.

- 종단선
- 밴드
- 라벨
- 설계고 계산
- 절성토 계산
- Profile 수정

현재 애드인에는 이미 `WallSpan`으로 수직부의 Front/Back 정보를 가지고 있으므로, Civil 3D 객체를 추가로 생성하기보다 기존 데이터를 표시용으로 활용하는 것이 더 적절하다.

---

## 10. Label Expression 방식도 주 해결책으로 추천하지 않음

Civil 3D Label Expression을 이용해 하나의 라벨에 두 값을 넣는 방법도 검토할 수 있지만, 기본 Expression은 해당 Label이 참조하는 객체의 값을 조합하는 용도에 가깝다.

따라서 다음과 같은 구조는 적합하지 않다.

```text
현재 Station의 계획고
+
같은 Station의 Wall Front Elevation
+
같은 Station의 Wall Back Elevation
```

특히 하나의 Profile에 존재하지 않는 두 개의 Elevation을 기본 Expression만으로 자연스럽게 가져오는 방식은 적합하지 않다.

따라서 이 문제는 Expression보다 애드인에서 직접 표시 데이터를 만드는 방식이 안정적이다.

---

## 11. 지반고는 한 줄을 유지

수직부라고 해서 원지반까지 두 줄로 만들 필요는 없다.

원하는 도면 표현은 다음과 같이 유지한다.

```text
계획고     184.10
           189.10
지반고     183.67
절성토고    -0.43
            -5.43
```

즉 내부 데이터도 다음과 같이 구성하는 것이 적절하다.

```csharp
VerticalGrade
{
    Station
    FrontDesignElevation
    BackDesignElevation
}
```

지반고에 대해서 별도의 Front/Back 데이터를 만드는 것은 피한다.

---

## 12. 실제 코드 수정 순서

한꺼번에 전체 구조를 변경하지 말고 다음 순서로 수정하는 것을 권장한다.

### ① WallSpan을 수직부 표시의 기준 데이터로 확정

```csharp
WallSpan
{
    Mid,
    Front,
    Back
}
```

그리고:

```csharp
FrontZ = pad.ElevationAt(Front);
BackZ  = pad.ElevationAt(Back);
```

를 통해 두 계획고를 확보한다.

### ② 계획고 BandStyleId를 확정

현재 사용 중인:

```csharp
sv.Bands.GetBottomBandItems()
```

방식을 이용해 계획고 BandStyle을 확정한다.

가능하면 `LabelGroup.StyleName`을 기준으로 계획고를 찾지 않는다.

### ③ 수직부 Station의 기본 계획고 표시를 숨김

Civil 3D LabelGroup API는 이 단계에서만 사용한다.

```csharp
se.Visibility = false;
```

### ④ 수직부 두 줄을 애드인에서 생성

```text
FrontZ
BackZ
```

두 값을 각각 표시한다.

### ⑤ 전용 레이어에서 관리

```text
DH_GRADING_VERTICAL_GRADE
```

레이어에 수직부 표기를 생성한다.

### ⑥ 변경 시 재생성

```text
기존 수직부 표기 삭제
        ↓
WallSpan 재계산
        ↓
Front / Back Z 재계산
        ↓
새 표기 생성
```

```text
                    DH.Grading
                        │
                 ┌──────┴──────┐
                 │             │
             일반구간        수직부
                 │             │
          Civil3D 기본밴드    WallSpan
                 │             │
             계획고 1개      Front / Back
                               │
                               ▼
                    VerticalGradeAnnotation
                               │
                         ┌─────┴─────┐
                         │           │
                    Front Text   Back Text
```

도면 결과는 다음과 같은 형태가 된다.

```text
측점          계획고
────────────────────
No.5+10       184.30

No.5+12.34    184.10
              189.10

No.5+15       189.30
```

## 14. 최종 판단

현재의 근본적인 판단은 큰 방향에서 맞다.

**"Profile은 한 Station에 하나의 표고를 가지므로 수직부의 두 계획고를 Profile 데이터 자체로 표현하려 하지 않는다."**

이 문제는 데이터 모델을 억지로 변경하는 것보다 **계산 데이터와 도면 표시 데이터를 분리**하는 것이 적절하다.

최종적으로 다음 원칙을 적용하는 것을 권장한다.

1. `Profile`은 계산용 단일 계획고로 유지
2. `WallSpan`은 수직부의 Front/Back 정보를 보유
3. 일반구간은 Civil 3D 기본 Band 사용
4. 수직부 Station은 기본 계획고 Label을 숨김
5. 수직부 두 계획고는 애드인에서 직접 표시
6. Y순서로 LabelGroup을 추정하는 방식은 제거
7. Band → BandStyleId 방향으로 계획고 Band를 식별
8. DBText는 전용 레이어에서 애드인이 관리
9. 변경 시 기존 Annotation을 삭제하고 재생성
10. 별도 Profile 두 개를 만드는 방식은 사용하지 않음

이 구조라면 현재 작성 중인 `DH.Grading`의 전체 구조를 크게 흔들지 않고, 다음 함수들을 중심으로 수정할 수 있다.

- `SheetCommand.WallBandPairs`
- `SheetCommand.SpreadBandLabels`
- `ProfileCommand.DrawVertBars`

특히 **`WallBandPairs`에서 수직부의 Front/Back 표고를 확정하고, `SpreadBandLabels`는 일반 밴드 처리에 집중시키며, 수직부 두 줄 표기는 별도의 함수로 분리하는 것**을 권장한다.
